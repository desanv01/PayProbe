## Interfaces for downstream workers
- Config: loadConfig(), credentialPresence(config), Config exported from src/core/config.ts. Defaults: simulated provider, loopback host, port 4310, public URL http://127.0.0.1:4310, .payprobe/payprobe.sqlite. Non-loopback binding requires PAYPROBE_API_TOKEN. Only PAYPROBE_PROVIDER=simulated is accepted; no automatic live fallback. Public env example values are blank; runtime defaults apply.
- Store(path): src/storage/database.ts; Node 24 built-in SQLite. db is exposed for additive phase migrations. Tables: runs, cases, events, orders, operations, entitlements, simulated_provider_orders (provider ctor). Methods: createRun(plan)->id, run(id), setRunState(id,state), appendEvent(runId,scenarioId|null,source,provenance,data), events(runId), order(purchaseId), operations(purchaseId), count(purchaseId), close(). Existing in_flight operations become uncertain on reopen. Events sequence per run starts at 1. Consumer must sanitize data before appendEvent; no raw secrets/prompts/PII.
- PaymentProvider interface: readonly provenance; create({purchaseId,amountCents,currency:'USD'},requestId), get(providerOrderId), capture(providerOrderId,requestId). Promise<PaymentOrder>; captures carry ID/status/amount/currency. Current provenance is strictly simulated. Future real implementation requires explicit extension of the provenance type and identity matching policy.
- SimulatedProvider(store,publicUrl): persisted independent provider ledger; adds approve(providerOrderId). Deterministic IDs, explicit approval, one capture. Read GET never approves. create/capture request IDs must retain exact identity on retry.
- SampleStore(store,provider): create(PurchaseInput,operationId), buyerReturn(purchaseId), capture(purchaseId,operationId), reconcile(purchaseId), observe(purchaseId), download(purchaseId,token). buyerReturn never captures; capture verifies matching provider purchase/order/merchant/USD amount and one completed capture. reconcile queries provider first and fulfills idempotently. TargetPaymentTransport suppresses one response after provider capture but before target business logic receives it. armFault/consumeFault stored in SQLite; fault fired persists across restart.
- PurchaseInput: purchaseId UUID, integer amountCents 1..10000, currency USD, productId sample-guide. Operation IDs UUIDs, persisted before mutation. Operation identity conflict returns HTTP 409; uncertain capture requires reconcile, never new capture/order. Entitlement unique by purchase and capture.
- buildServer(config,suppliedStore?) -> {app,db,provider,target,ai}. app is Fastify (unstarted; app.inject supported). Caller-supplied Store stays caller-owned. No raw requests/errors/provider messages logged.
- DeepSeekClient(config).json<T>(system,input,zodSchema,example,attempts=2) -> {data,metadata}. Official fixed https://api.deepseek.com endpoint, explicit key, maxRetries 0, at most two attempts/40s overall/1200 output tokens. Thinking disabled. No fallback. Blank, truncation, invalid JSON/schema rejected; auth HTTP errors not retried. probe() forces one attempt. Caller supplies bounded sanitized input and semantic validation; P3 owns planning/explaining.
- CLI currently: doctor, serve, deepseek-probe; P3 exports commands for P1 integration. No styled UI.

## HTTP adapter v1.0
All endpoints except /health require Authorization: Bearer PAYPROBE_API_TOKEN when configured. Local loopback-only mode permits owner requests without it. Set a token for remote use.
- GET /health; GET /api/doctor; POST /api/deepseek/probe (one real call).
- GET /adapter/capabilities: version, capability list, provider/provenance.
- POST /adapter/orders: {purchaseId,operationId,amountCents,currency?,productId?}.
- GET /adapter/orders/:purchaseId: observed state/amount/provider ID/approval URL/count/access/fault status/provenance (no verdict).
- POST /adapter/orders/:purchaseId/buyer-return (no capture).
- POST /adapter/orders/:purchaseId/capture: {operationId}.
- POST /adapter/orders/:purchaseId/reconcile and /process-again: target queries current provider state.
- POST /adapter/orders/:purchaseId/arm-fault: one-time completed capture response suppression.
- GET /adapter/orders/:purchaseId/check-download: {accessible,provenance}; GET /adapter/orders/:purchaseId/operations.
- GET /api/orders/:purchaseId/download-link: owner access returns capability URL. GET /adapter/orders/:purchaseId/download?token=... checks token AND entitlement. With API auth enabled, bearer is also required. Do not publish capability tokens in evidence.
- GET /simulated/orders/:providerOrderId/approve only explains simulator POST action; POST same URL explicitly approves. No fake PayPal login/page.
- GET /provider/orders/:providerOrderId independently reads simulated provider ledger without calling target processing. Evaluator must use this, never target fixture logic.
