# P2 handover — simulated scenario runner

Updated 2026-11-10. Implementation complete, integration owned by main. Payment provenance is **simulated** throughout. No PayPal network calls, credentials, buyer verification or submission-readiness claims.

## Interfaces and connections

- `src/runner/index.ts`: `run({store,adapter,plan,autoApproveSimulated?})`, `resume({store,adapter,runId,autoApproveSimulated?})`, `report(store,runId)`.
- `src/runner/types.ts`: `runnerPlanSchema`, `RunnerPlan`, `Adapter`, `RunReport`, evidence and five verdict types. Strict plan: version `1.0`, selected `S1`–`S4` IDs, amountCents, USD currency, sample-guide productId, bounded fulfillmentTimeoutMs, optional disclosed fixtureMode (`corrected`, `premature_fulfillment`, `duplicate_processing`). Defaults supplied by schema. P3 imports this contract and maps reviewed plan fields.
- `src/adapters/http.ts`: `new HttpAdapter({baseUrl,token?,fetch?,timeoutMs?})`. Requests use versioned P1 HTTP routes with strict observation parsing, timeout, no redirects and sanitized error codes. No target decision imports.
- Default run waits in `awaiting_approval`; `report.approvals` identifies pending simulated purchase/link. Approval must use explicit simulator POST; GET does not approve. `autoApproveSimulated:true` explicitly allows simulated-only headless approval.
- SQLite tables `runner_runs`, `runner_steps`, `runner_evidence`, `runner_results` extend supplied Store without modifying P1 storage. IDs derive stably from run identity. S1–S3 share order A, S4 uses order B. Execution uses canonical S1–S4 order regardless of plan selection ordering.
- Reports include plan hash, adapter version, timestamps, ordered evidence, exact evidence IDs `${runId}:${sequence}`, sources, results and provenance. P3 owns public report projection/AI explanation; no fixture-mode-based verdict branches.

## Implemented behavior

- S1 establishes independent APPROVED with no capture before buyer return; checks zero entitlement and inaccessible download afterward. Missing preconditions are INCONCLUSIVE.
- S2 captures via target, independently checks identity/merchant/amount/currency/completed capture, polls actual target fulfillment within declared bounded interval, requires exactly one accessible entitlement.
- S3 establishes paid precondition then invokes target processing three times, checking delivery and same provider capture after every call. Sequential scope only.
- S4 arms P1 one-time transport fault, records suppressed response and uncertain unfulfilled target, independently verifies existing capture, asks target to reconcile and checks one delivery with unchanged capture identity. Runner never repairs target state itself.
- Interrupted pending capture is never blindly repeated. Resume observes the provider and invokes target reconciliation only when matching completion is established; otherwise INCONCLUSIVE. Create retries use exact persisted simulator identities. Run executor prevents duplicate same-process execution; no distributed/concurrent execution guarantees.
- PASS/FAIL/INCONCLUSIVE/UNSUPPORTED/ERROR are separate from lifecycle. Finished/error case results are retained; resume does not rerun completed cases. A fresh run is needed to retry a completed inconclusive/error diagnostic after changing the target.
- Seeded fixture config is passed only at create; assertions evaluate actual provider/application/download observations. P1 owns actual fixture storage/behavior.
